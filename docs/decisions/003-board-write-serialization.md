# 003. 보드 단위 쓰기 직렬화와 seq 발급 위치

- 상태: 채택
- 날짜: 2026-10-12
- 단계: Phase 2 (Phase 4·5에서 활용)

## 배경

- 두 사용자가 같은 두 카드 사이로 각자 다른 카드를 동시에 옮기면, 같은 이웃을 기준으로 계산해 **같은 position**이 나올 수 있다.
- 실시간 이벤트의 `seq` 순서가 DB 커밋 순서와 다르면, 클라이언트가 이벤트를 seq 순서대로 적용했을 때 서버와 다른 상태로 수렴한다.

## 선택지

1. 카드 행에만 낙관적 잠금(version)을 건다. 이웃 카드끼리의 position 충돌은 막지 못한다.
2. 리스트 행 잠금: 리스트 간 이동 시 잠금 2개가 필요하고 교착 위험이 있다.
3. **보드 행 잠금** (`SELECT ... FOR UPDATE`): 보드 내 모든 쓰기를 직렬화한다.
4. 직렬화 격리 수준(SERIALIZABLE) + 재시도: 재시도 로직이 복잡하고, 충돌이 잦으면 처리량이 오히려 떨어진다.

## 결정

- 모든 보드 쓰기는 `BoardWriter.write()`를 거친다.
  - 순서: `BEGIN → 보드 행 FOR UPDATE → 변경 → Redis INCR로 seq 발급 → Activity 기록 → COMMIT → 이벤트 로그 기록 + 브로드캐스트`
- 스냅샷 조회(`GET /boards/:id`)는 보드 행을 `FOR SHARE`로 잠근 뒤 seq와 데이터를 읽는다.

## 이유

- seq를 잠금 안에서 발급하므로 **seq 순서 = 커밋 순서**가 된다.
- 스냅샷의 seq 이하 이벤트는 모두 데이터에 반영되어 있고, 그보다 큰 이벤트는 반영되어 있지 않다. 그래서 "스냅샷 + 이후 이벤트"가 정확히 맞아떨어진다.
- 칸반은 보드당 동시 쓰기가 많지 않다(사람 손으로 하는 조작). 보드 단위 직렬화의 비용은 작고 정합성 이득이 크다. 부하 테스트 결과는 `docs/performance.md`에 있다.

## 트레이드오프

- 한 보드에 초당 수백 건의 쓰기가 몰리면 잠금 대기가 생긴다. 이 경우 리스트 단위 잠금으로 세분화할 수 있다.
- 트랜잭션이 seq 발급 후 롤백되면 seq에 빈 번호가 생긴다. 클라이언트는 sync 응답의 seq로 이 공백을 건너뛴다.
