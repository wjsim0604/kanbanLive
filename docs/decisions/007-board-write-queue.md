# 007. 인스턴스 내 보드별 쓰기 대기열 (KeyedSemaphore)

- 상태: 채택
- 날짜: 2026-10-12
- 단계: Phase 7

## 배경

부하 테스트에서 한 보드에 쓰기가 몰렸다. 그 보드의 요청들이 DB 커넥션을 잡은 채 보드 행 잠금을 기다리면서 커넥션 풀이 고갈되었고,
**관계없는 다른 보드의 p95가 565ms**까지 올라갔다 (docs/performance.md).

## 선택지

1. 커넥션 풀 크기 증가: 대기하는 요청 수만큼 커넥션이 필요하다. 근본 해결이 아니고 DB 커넥션 한도에 걸린다.
2. 잠금 대기 타임아웃(`lock_timeout`) + 재시도: 실패와 재시도가 늘고 지연 분포가 나빠진다.
3. **인스턴스 내 보드별 대기열**: DB 커넥션을 잡기 전에 메모리에서 기다린다.
4. 보드별 큐 워커(BullMQ 등): 쓰기 응답이 비동기가 되어 REST 의미가 복잡해진다.

## 결정

- `BoardWriter.write()`가 `KeyedSemaphore(permits = 2)`를 거쳐 트랜잭션을 시작한다.
- permits = 1은 잠금 인계 사이에 커넥션 획득과 BEGIN이 직렬 구간에 들어가 처리량이 떨어진다. permits = 3은 다른 보드의 지연이 다시 늘었다. 그래서 **2**로 정했다(`BOARD_WRITE_CONCURRENCY`로 조정 가능).
- 인스턴스 간 정합성은 기존처럼 DB 행 잠금(`FOR UPDATE`)이 보장한다. 대기열은 성능 최적화일 뿐이고 정합성의 근거가 아니다.

## 결과

- 핫 보드 시나리오에서 다른 보드 p95 564ms → **61ms**, 전체 처리량 175 → **245 moves/s**
- 현실적 다중 보드 시나리오에서 p95 96ms → **72ms**
