# 성능 측정 (Phase 7)

카드 이동은 이 앱에서 가장 빈번하고 지연에 민감한 작업입니다. 이동이 서버에서 확정되고, 같은 보드의 다른 사용자 화면에 반영되기까지의 시간을 측정했습니다.
병목을 찾아 개선한 뒤 같은 조건으로 다시 측정했습니다.

## 측정 방법

- 도구: `load/move-latency.ts` (Node + socket.io-client로 직접 작성)
  - k6/Artillery로는 "A가 보낸 이동 이벤트가 B의 소켓에 도착하기까지"를 재기 어려워서 직접 만들었습니다.
- 각 클라이언트는 Socket.IO로 보드에 접속해 있고, 자기 카드 5장 중 하나를 `INTERVAL_MS`마다 무작위 리스트로 옮깁니다(`POST /api/cards/:id/move`).
- 측정 항목

| 항목        | 정의                                                                                                              |
| ----------- | ----------------------------------------------------------------------------------------------------------------- |
| request     | 이동 요청 → HTTP 응답                                                                                             |
| propagation | 이동 요청 → **같은 보드의 다른 클라이언트**가 `card:moved` 이벤트를 받기까지                                      |
| error rate  | 실패한 요청 비율                                                                                                  |
| converged   | 종료 후 각 클라이언트 상태(초기 스냅샷 + 수신 이벤트를 `applyBoardEvent`로 적용)가 DB 스냅샷과 같은 클라이언트 수 |

- 환경: 4 vCPU 컨테이너 1대에서 api 1개, PostgreSQL 16, Redis 7, 부하 발생기를 모두 실행. 각 30초. 절대 수치보다 **개선 전후 비교**에 의미가 있습니다.
- 재현 방법

```bash
pnpm build && node apps/api/dist/main.js &          # api 실행 (apps/api/.env)
CLIENTS=50 BOARDS=10 DURATION_SEC=30 INTERVAL_MS=250 LABEL=multi \
  OUT=load/results/multi.json pnpm --filter @kanban/load move-latency
```

원본 결과는 `load/results/*.json`에 있습니다.

> 모든 시나리오에서 에러 0%, **모든 클라이언트가 DB와 같은 최종 상태로 수렴**했습니다.

## 병목 분석

### 1. 계측

`BoardWriter.write()`에 구간별 타이머를 임시로 넣고, 단일 보드 50명 부하에서 이동 1건당 평균을 쟀습니다.

| 구간                                                         | 평균      |
| ------------------------------------------------------------ | --------- |
| `$transaction` 호출 → 콜백 시작 (**커넥션 풀 대기 + BEGIN**) | **155ms** |
| 보드 행 잠금 대기 (`SELECT ... FOR UPDATE`)                  | 61ms      |
| 잠금 보유: 조회·갱신 쿼리                                    | 6.2ms     |
| 잠금 보유: seq 발급(Redis INCRBY)                            | 0.3ms     |
| 잠금 보유: 활동 로그 INSERT                                  | 1.2ms     |
| COMMIT                                                       | 1.3ms     |
| 이벤트 기록 + 브로드캐스트                                   | 1.3ms     |

같은 시간에 api 프로세스는 CPU 70~140%를 썼고 PostgreSQL은 프로세스당 10~20%로 여유가 있었습니다.

### 2. 원인

- 같은 보드에 대한 쓰기 요청들이 **DB 커넥션을 하나씩 잡은 채** 보드 행 잠금을 기다렸습니다.
- Prisma 커넥션 풀은 기본 `CPU × 2 + 1 = 9`개입니다. 한 보드의 대기 요청만으로 풀이 바닥났습니다.
- 그 결과 권한 확인 쿼리나 **다른 보드의 쓰기**까지 풀을 기다렸습니다. 이것이 핫 보드 시나리오에서 cold 보드 p95가 565ms로 치솟은 원인입니다.

### 3. 개선

1. **쿼리 축소** (`012ba4b`)
   - 권한 확인: `boardIdOfCard` + `requireRole` 2회 → `requireCardRole` 1회(join으로 보드와 멤버십을 함께 조회)
   - 잠금 구간: `update ... include { list, _count }`(join + count 서브쿼리)를 일반 `update`로 바꿨습니다. 응답 DTO의 `boardId`와 댓글 수는 이미 읽은 값으로 채웁니다.
   - 효과: 단일 보드 처리량 +9%
2. **인스턴스 내 보드별 대기열** (`KeyedSemaphore`, 보드당 동시 2)
   - 같은 보드의 쓰기는 **DB 커넥션을 잡기 전에 메모리에서** 줄을 섭니다.
   - 동시 1이면 커넥션 획득과 BEGIN까지 직렬 구간에 들어가 핫 보드 처리량이 56/s로 떨어졌습니다.
   - 동시 2(하나는 잠금 보유, 하나는 바로 뒤에서 대기)일 때 잠금 인계가 빨라 65/s가 나왔습니다. 동시 3은 오히려 cold p95가 99ms로 나빠져 **2로 정했습니다** (`BOARD_WRITE_CONCURRENCY`).
   - 여러 인스턴스 사이의 정합성은 여전히 DB 행 잠금이 보장합니다. 대기열은 순수한 성능 최적화입니다.
3. **느린 쓰기 경고 로그**: 잠금 보유가 `SLOW_WRITE_MS`(기본 100ms)를 넘으면 `slow board write` 경고를 구조화 로그로 남겨 운영 중 병목을 찾을 수 있게 했습니다.

## 남은 과제

- 단일 보드 처리량 상한(약 100 moves/s) 올리기
  - 잠금 보유 구간의 쿼리(카드·리스트·형제 조회)를 SQL 하나로 합치거나, 활동 로그를 커밋 후 비동기로 기록하면 보유 시간을 더 줄일 수 있습니다.
- Docker 이미지 769MB
  - 대부분이 Prisma(클라이언트 엔진 + 마이그레이션용 CLI)입니다.
  - 마이그레이션 전용 이미지를 분리하거나 Prisma 7의 driver adapter로 옮기면 크게 줄일 수 있습니다.
- 브로드캐스트 비용
  - 보드 접속자가 수백 명 규모가 되면 이벤트 하나당 전송 비용이 커집니다.
  - 이벤트 배치(같은 틱의 이벤트를 묶어 전송)를 검토할 만합니다.
